## What is engineered

Dedicated V6-S1 **LIVE broker order transport candidate**, separate from the hard-locked V5 14-ETF BUY-notional writer. It only understands hypothetical quantity SELL of exactly one original non-overlap position **ACWI, EEM or XLV**, and refuses XLE, new sector ETFs, buys, notional order fields, shorts, leverage or batch retries.

Pure original-order payload is `symbol`, `qty` (decimal <=9 places), `side=sell`, `type=market`, `time_in_force=day`, `extended_hours=false` and unique deterministic V6 migration `client_order_id`. Official Alpaca fractional-share guidance confirms fractional qty, DAY and market-order eligibility. Broker API order-by-client-id endpoint makes idempotent recovery possible. Source: https://docs.alpaca.markets/us/docs/fractional-trading and https://docs.alpaca.markets/us/reference/getorderbyclientorderid-1

**Two independent hardcoded FALSE controls** `TRANSPORT_RELEASED` and `PUBLIC_EXECUTION_ENABLED`. A public call will ALWAYS throw before credentials or network; internal actual GET/POST transports each check the hardcoded network gate FIRST, independently. No GitHub workflow supplies Alpaca credentials or calls the new executable; tests use only offline fixtures. This is NOT an approved LIVE order release.

## Status/failure behavior

1. Validate exact symbol, original quantity >0, max 9 decimal places, deterministic client ID, no extra order fields, no notional/BUY/XLE instructions. Missing/changed quantities fail.
2. Matching already-existing broker receipt by client ID has status `filled`, `accepted/new/pending_new/partially_filled/pending_cancel`, `canceled/expired/rejected/replaced/held` or unknown. For **every** existing status, **NEVER POST the same ID again**. Only a **full** broker filled quantity and original position confirmed flat after a fresh GET can certify a completed exit. A filled receipt while the original position still exists is inconsistent and triggers reconciliation stop.
3. An unknown POST outcome, timeout, receipt not found after previous journaled attempt, or `404` client ID lookup without evidence of a never-attempted journal must **never** lead to automatic resubmission. A durable, uniquely reserved migration ledger **before any future POST** plus serialized controller, source-fresh account GET, remote stopped/live-release approval and source-matched position/fill evidence will be required in a separately reviewed future implementation. This candidate may construct/review a hypothetical payload but cannot take the next step.
4. No bulk legacy liquidation. A future approved release will progress in order ACWI, EEM, XLV, with an independently reverified settled-cash gate and XLE preserved. Every order submission must have exact prior position and risk-clearance time. Staged controller `fund100_v6_s1_staged_controller_core_v1_0.py` remains offline/fake and does NOT inherit this candidate's capability.
